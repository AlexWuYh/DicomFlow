# 开发规范（供 AI / 代理阅读）

本文档描述 DicomFlow 的**里程碑驱动开发**、分支管理、PR 目标与发布流水线约定。实现代码时默认遵守；**不要**把本节内容写进用户向 README。

## 里程碑模式（强制）

开发按**里程碑（Milestone）**推进，而不是无边界的大堆需求并行。AI 与贡献者默认采用下列规则。

### 原则

1. **一次聚焦一个里程碑**  
   当前进行中的工作应能映射到：GitHub Milestone，和/或 [06-roadmap.md](./06-roadmap.md) 中某一 Phase 的明确条目。不要在同一会话/同一 PR 里混装多个里程碑的大功能。

2. **里程碑有边界**  
   每个里程碑必须可说清：
   - **目标**（做成什么）
   - **范围内 / 范围外**（明确不做的）
   - **完成标准**（可验证：测试、手工冒烟、配置项等）
   - **交付物**（代码、`.ai` 文档更新、版本是否 bump）

3. **先对齐再写代码**  
   用户提出新需求时：先判断属于哪个里程碑 / 是否应新开里程碑；若与当前里程碑无关或冲突，先说明并征求确认，避免静默扩大范围。

4. **里程碑内再拆任务**  
   里程碑内部用短分支与小 PR（`feature/*`、`fix/*`）推进；每个 PR 只解决里程碑内的一块可审查改动。合入 `dev` 即视为该块完成，不代表整个里程碑结束。

5. **里程碑结束才谈发布**  
   - 里程碑内日常合入 **`dev`**。  
   - 仅当里程碑（或用户明确要求的可发布切片）达成完成标准后，再升版本号并将 `dev` → **`main`** 做 Release。  
   - 禁止为半成品里程碑随意打正式 Release（用户明确要求 pre-release / 例外时除外）。

6. **与路线图同步**  
   - 路线图阶段见 [06-roadmap.md](./06-roadmap.md)。  
   - 完成或调整某 Phase 条目时，更新该文档勾选状态与说明。  
   - 若使用 GitHub Milestones / Issues：标题与描述应能对应路线图或独立里程碑目标；关闭 Issue 时确认完成标准已满足。

### AI 执行清单（接到开发任务时）

| 步骤 | 动作 |
|------|------|
| 1 | 识别所属里程碑（GitHub Milestone / roadmap Phase / 用户命名的目标） |
| 2 | 用几句话复述范围与完成标准；范围不清则先问，不瞎做 |
| 3 | 仅实现范围内事项；范围外记到「后续里程碑」勿顺手实现 |
| 4 | 分支从 `dev` 拉；PR 目标为 `dev` |
| 5 | 达到完成标准后更新 `.ai`（路线图勾选、相关规格） |
| 6 | 用户要求发布且里程碑可交付时，再 bump 版本并走 `main` Release |

### 反模式（禁止）

- 无里程碑语境下连环大改架构 + 功能 + 重构混在一个 PR  
- 借「小修」塞进另一里程碑的大功能  
- 未达成完成标准就合 `main` 并制造新版本号  
- 修改行为与 `.ai` 规格不一致却不更新文档  

## 分支模型

| 分支 | 职责 |
|------|------|
| **`main`** | **发布**主分支。只合入可发布代码。每次 push 触发 Release 打包流水线。 |
| **`dev`** | **开发**集成主分支。日常功能合并到这里。GitHub 默认分支为 `dev`。 |
| **`feature/*`**、**`fix/*`**、**`chore/*`** 等 | 从 **`dev` 拉取** 的短期分支。 |

```
feature/* ──┐
fix/*     ──┼──► dev ──(发布)──► main ──► GitHub Release + sdist/wheel
chore/*   ──┘
```

## 开发流程（强制）

1. 基于最新 `dev` 开分支（`feature/…`、`fix/…` 等），**禁止**直接在 `main` 上开发功能。
2. 功能开发完成后，开 PR **目标分支 = `dev`**（不要对 `main` 开功能 PR）。
3. CI（`.github/workflows/ci.yml`）在以下情况跑测试：
   - push 到 `dev`
   - PR 指向 `dev` 或 `main`
4. 需要发布时：
   - 在 `dev` 上升版本：`pyproject.toml` 的 `project.version` 与 `src/dicomflow/__init__.py` 的 `__version__` 保持一致
   - 将 `dev` 合并到 `main`（PR 或约定流程）
5. `main` 上有提交后，Release 流水线（`.github/workflows/release.yml`）会：
   - 跑测试
   - 构建 sdist + wheel，上传 workflow artifacts
   - 若标签 `v{version}` **尚不存在**，则创建 GitHub Release 并附带安装包
   - 若标签已存在（未升版本号），仍打包 artifacts，**不**重复建 Release

## 版本号

- 语义化版本：主.次.修订（当前见 `pyproject.toml`）
- 新 Release 标签格式：`v{version}`（如 `v0.2.0`）
- 合入 `main` 前若期望产生新 GitHub Release，必须先升版本号

## AI 改代码时的默认行为

| 场景 | 默认 |
|------|------|
| 功能 / 修复 / 文档（开发态） | **先挂到里程碑**；在 `dev` 上工作；新分支从 `dev` 拉 |
| 用户一次性提很多需求 | 按里程碑拆分优先级；只做当前里程碑，其余列入后续 |
| 发布相关提交 | 确认里程碑可交付 → 版本号改在 `dev` → 再合 `main`；不要只在 `main` 上堆功能 |
| 用户说「提交 / push」且未指定分支 | 推送到当前工作分支；若在错误分支上（如误在 `main` 做功能），先切到 `dev` 或 feature 分支再说明 |
| 用户明确要求发布 | 核对完成标准与版本号 → 合入 `main` → 依赖 GitHub Actions 出包 |

## 相关工作流文件

| 文件 | 触发 | 作用 |
|------|------|------|
| `.github/workflows/ci.yml` | `dev` push；PR → `dev`/`main` | pytest（Python 3.11 / 3.12） |
| `.github/workflows/release.yml` | `main` push | 测试 + 构建包 + 条件创建 Release |
